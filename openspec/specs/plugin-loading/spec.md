## Purpose

让用户与第三方在不修改平台源码的前提下，以向插件目录放置 jar 的方式为平台增加新的构建执行器与交付 Provider——运行时可插拔的第一阶段（重启期加载），并对坏插件与版本不兼容提供隔离与可观测。

## Requirements

### Requirement: 插件打包约定
插件 SHALL 为单个 jar 文件，同时满足：内含至少一个受支持扩展点的 `META-INF/services` 注册声明；manifest 携带 `Plugin-Id`（唯一标识）、`Plugin-Version`、`Extension-Api-Version` 三项属性。不满足约定的 jar 视为无效插件。

#### Scenario: 合法插件 jar
- **WHEN** 一个 jar 含 `DeliveryProvider` 的 services 声明且 manifest 三属性齐备
- **THEN** 该 jar 被识别为有效插件，进入加载流程

#### Scenario: 缺失 manifest 属性
- **WHEN** 一个 jar 的 services 声明完好但缺少 `Plugin-Id` 属性
- **THEN** 该 jar 被判定为无效插件，失败原因记录"缺少 Plugin-Id"，不进入加载

### Requirement: 启动发现与加载
平台启动时 SHALL 扫描配置的插件目录，加载全部有效插件的扩展实现并注册到对应扩展点注册表；插件贡献的构建类型/交付模式经既有 API 立即可见。插件目录为空或不存在时，平台 MUST 正常启动且行为与无插件时一致。

#### Scenario: 放置插件后重启生效
- **WHEN** 将一个提供新交付模式 P 的插件 jar 放入插件目录并重启平台
- **THEN** 交付模式查询 API 中出现 P，且可对目标环境发起 P 模式的交付

#### Scenario: 空插件目录
- **WHEN** 插件目录不存在或为空
- **THEN** 平台正常启动，日志无错误，功能与内置扩展一致

### Requirement: 版本兼容判定
每个插件 MUST 声明其构建所依据的扩展 API 版本；平台 SHALL 在加载前校验兼容性（主版本一致且插件声明的次版本不高于平台提供者），不兼容插件被拒绝加载，错误信息 MUST 同时包含插件标识、插件声明版本与平台实际版本。

#### Scenario: 兼容插件通过
- **WHEN** 插件声明 `Extension-Api-Version` 与平台扩展 API 主次版本一致
- **THEN** 插件正常加载并注册

#### Scenario: 主版本不兼容被拒
- **WHEN** 平台扩展 API 主版本为 2，插件声明主版本为 1
- **THEN** 插件被拒绝加载，错误信息列出插件 id、声明的 1.x 与实际的 2.x

### Requirement: 失败隔离
单个坏插件（jar 无法读取、声明的类不存在、实例化抛异常、services 声明格式错误）MUST NOT 阻止平台启动，也 MUST NOT 影响其他插件的加载；每类失败 SHALL 逐插件记录原因。

#### Scenario: 坏插件与好插件并存
- **WHEN** 插件目录中同时存在一个损坏 jar 与一个有效插件
- **THEN** 平台正常启动，有效插件加载成功，损坏 jar 出现在失败清单中并注明读取失败原因

#### Scenario: 实例化异常不扩散
- **WHEN** 某插件实现的构造过程抛出运行时异常
- **THEN** 该插件记为失败并记录异常摘要，其余插件与平台功能不受影响

### Requirement: 插件清单查询
系统 SHALL 提供插件清单 API：列出已加载插件（标识、版本、贡献的扩展点及数量）与失败插件（标识或文件名、失败原因），无需访问运行日志即可获知插件状态。

#### Scenario: 混合加载后查询
- **WHEN** 一次启动中加载了两个成功插件与一个失败插件后查询清单
- **THEN** 返回两个加载成功条目（含各自贡献的扩展点）与一个失败条目（含原因）

### Requirement: 插件禁用
系统 SHALL 支持不经删除的禁用方式：将插件 jar 移入插件目录下的禁用子目录（或按平台约定的改名方式）后，下次启动不再加载该插件；平台 MUST 在文档中明确该约定。

#### Scenario: 禁用后重启
- **WHEN** 将已加载插件的 jar 移入禁用目录并重启
- **THEN** 该插件不再出现在已加载清单，其贡献的扩展点从 API 中消失，其余插件不受影响
